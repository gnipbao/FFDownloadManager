# Rust MVP 首轮速度验证

日期：2026-09-21。实现：Rust 命令行 MVP；下载引擎为未修改的 gosh-dl 0.6.3，仅启用 HTTP 与存储功能，显式开启 reqwest 的 HTTP/2 feature。

**初步结论：现成 Rust 下载内核已显示出处理千兆级数据的余量，值得继续做产品 MVP；当前结果不能证明公网跑满千兆，也不能证明超过 Neat。**

## 已实现与验证

- `ffdm download`：HTTP(S)、可配置 1–16 路、临时文件、完成同步和 SHA-256、拒绝覆盖。
- `ffdm resume`：从保存的会话恢复；终端 Ctrl-C 或 `--pause-after` 可保存退出。
- `ffdm probe`：使用 Rust HTTP/TLS 栈检查状态、长度和探测请求的协商协议；HEAD 失败时尝试一字节 Range GET，不下载完整文件。
- `ffdm bench`：Rust 回环服务器、Rust 单流对照、顺序轮换测试、原始 JSON。
- 5 个集成测试通过，覆盖多段字节一致性、不覆盖、两个独立 CLI 进程之间暂停恢复、无 Range 下载、错误 Range 安全回退、摘要不匹配时不发布文件，以及 HEAD 失败后通过 Range 获取总长度。
- release 构建、Clippy（warnings 视为错误）、rustfmt 检查已执行；实际命令见 README。

源码未改动上游下载调度，不包含自研自适应连接或慢尾段工作转移。界面、浏览器接管和完整桌面打包不在本轮 MVP 中。

## 环境与口径

环境为 macOS 26.6.2、arm64，Rust 1.98.1，release + thin LTO。内核 gosh-dl 0.6.3，HTTP 客户端 reqwest 0.13.5。依赖由 Cargo.lock 固定。

本地样本为 64 MiB 的确定性伪随机字节。每场景预热一次，每客户端测 3 轮并轮换顺序，共 24 个计入统计的样本。所有样本校验同一 SHA-256：

```text
a0e6fe14c4464e95b598a510d0a98d615133bd239f85938a62f31c1610bd54fd
```

主要耗时从建立下载任务开始，包含探测、传输、文件同步和 SHA-256。服务器数据生成、预热和样本清理不计入。Mbps 为十进制兆比特每秒，MB/s = Mbps ÷ 8；MiB 文件大小使用二进制单位。

本地服务和客户端同机，HTTP/1.1，无网络 TLS，OS 缓存经过预热。服务端统计了 Range 请求数：gosh 的 1/4/8 路样本分别发出 1/4/8 个 Range 请求。该计数不能等同于网络抓包验证的独立 TCP 连接数量。

## 本地受控场景

服务端将**每个响应**限为约 100 Mbps，不限制所有响应的合计速率；这是应用层定时发送，不是 100 Mbps 物理链路。

| 客户端 | 完成时间中位数 | 有效速度中位数 | 换算 MB/s |
| --- | ---: | ---: | ---: |
| Rust 单流对照（reqwest，1 MiB 缓冲） | 5.578 秒 | 96.2 Mbps | 12.0 |
| gosh-dl，1 路 | 5.593 秒 | 96.0 Mbps | 12.0 |
| gosh-dl，4 路 | 1.578 秒 | 340.3 Mbps | 42.5 |
| gosh-dl，8 路 | 0.918 秒 | 584.9 Mbps | 73.1 |

本场景中，8 路全流程有效吞吐约为 1 路的 6.1 倍。这个倍数只描述本实验：服务器特意允许多路合计获得更高吞吐，不能推广为普通互联网下载都加速 6 倍。

并发总额没有达到简单相乘的 800 Mbps；总计时包含初始化、同步、摘要与调度等开销。尚未 profiling，不将差距具体归因于某一个模块。

## 不限速回环场景

| 客户端 | 完成时间中位数 | 有效速度中位数 |
| --- | ---: | ---: |
| Rust 单流对照 | 0.262 秒 | 2052.4 Mbps |
| gosh-dl，1 路 | 0.255 秒 | 2102.2 Mbps |
| gosh-dl，4 路 | 0.271 秒 | 1981.1 Mbps |
| gosh-dl，8 路 | 0.255 秒 | 2108.2 Mbps |

结果集中在约 2 Gbps，说明本机短样本处理能力有余量；多路并未稳定优于单路。每次只有约四分之一秒，容易受调度和同步时机影响，因此不据此排列 1/4/8 路优劣，也不作为持续大文件、HTTPS 或公网性能上限。

## 用户提供的链接

用户提供的签名链接在北京时间 2026-09-21 15:13 左右，普通 GET 与 Range GET 均返回 HTTP 404、长度 0。查询中的 exp 若按 Unix 毫秒解释，为当天 14:36:12，早于测试时间；过期是可能原因，但仅凭响应无法确认服务端的具体拒绝原因。

因此没有把这个链接计入速度结果，也没有尝试更改签名参数。记录只保留隐藏查询参数后的来源，见 `benchmarks/user-source-probe.json`。

## 公网补充测试

公开源的初次连接出现过 TLS/HEAD 失败，最终选用 [Rust 官方编译器发布文件](https://static.rust-lang.org/dist/rustc-1.98.1-aarch64-apple-darwin.tar.xz)，大小 48,951,152 字节，约 46.68 MiB。HEAD 探测协商 HTTP/2 并返回 `Accept-Ranges: bytes`；没有抓包确认后续每个下载请求的协议及实际 TCP 连接数量。

| 请求的并发上限 | 完成时间 | 全流程有效速度 | 换算 MB/s |
| --- | ---: | ---: | ---: |
| 1 | 28.142 秒 | 13.92 Mbps | 1.74 |
| 4 | 42.313 秒 | 9.26 Mbps | 1.16 |
| 8 | 42.703 秒 | 9.17 Mbps | 1.15 |

3 次下载都成功，文件长度一致，SHA-256 均为 `738e3f60114b20550fcf4f8a57c9cea0544239f214709f45594ff3fde327f577`。首个完整样本作为后续一致性参照，本次没有用发布方签名或摘要验证来源真实性。

**这个公开源在本次单轮中，1 路比 4/8 路更快。** 公网只测 1 轮，顺序是 1→4→8，未消除 CDN、缓存和时段波动影响，不能据此确定稳定排名或将差距归因于 HTTP/2。它能证明“固定增加分段不保证更快”，不能测定用户宽带物理上限。

真实 HTTPS 结果独立保存于 `benchmarks/public-results.json`。总下载约 147 MB，完成的临时文件已清理。不可用来源的探测记录保存在 `benchmarks/public-source-probes.json`。

## 后续判断

本轮验证支持先用现成 gosh-dl 继续开发 MVP。优先补足 1 GiB 以上、HTTPS、睡眠唤醒、强杀进程和不同站点的测试，再决定是否需要更换或修改核心调度。默认并发不应仅因这次 8 路在限流场景胜出就对所有站点固定为 8。

尚未实测 Neat，尚未测 CPU、RSS、耗电、断电持久性或完整 HTTPS 协议／连接行为。所有原始样本在 `benchmarks/local-results.json`，环境摘要在 `benchmarks/environment.json`；使用与复现命令见项目 README。
